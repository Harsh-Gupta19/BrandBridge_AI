The one rule that keeps this project shippable

Every AI component in BrandBridge is replaceable by a deterministic fallback. The LLM parser falls back to a form. Social APIs fall back to manual profile entry. Semantic retrieval falls back to SQL category filters. If you cannot demo the flow with the AI switched off, the flow is not done — because on demo day something will be rate-limited.

What this manual adds that the existing documents do not have

  • A repo-anchored gap list. Part 1 compares the target design against the 200 files that exist today, so nobody re-designs what is already built or assumes something exists that does not.

  • Step-level construction order. Part 7 walks each flow from the screen down to the SQL, with the file to open at every step.
  • A UI review with the missing screens named. Part 9.

1.2 Three decisions to close in weekend 1

These are not research questions. They are build-blocking and each has a recommended answer you can adopt in ten minutes.

D1 · Identity model

Question: single role per user, or one account with two activatable profiles?

Recommendation: one account, two profiles. The wireframes, the demo script and the reciprocal research story all require a user to switch modes. Cost: one extra table, one migration, one X-Active-Role header.

D2 · Third platform

Question: Bluesky is in the repo but in none of the documents. Keep it?

Recommendation: keep it as a third adapter, not a third product surface. It has an open, key-free API, which makes it the most reliable demo-day data source you have. Declare it in an ADR and normalise it through the same contract.

D3 · The Wall settled

Decided: the Wall ships. It is a peer community where brands and creators post ideas, open calls and results, follow each other and reply in threads — the surface that attracts people to the platform before any campaign exists.

Two constraints keep it safe: wall content never enters the ranking pipeline, and a thread converts into an ordinary proposal rather than becoming a second negotiation channel. Cost: four tables, eight endpoints, two screens. See §5.12 and F13.

1.4 Two repository problems to fix in weekend 1

Problem 1 — the working tree is 509 MB

data/raw/ holds 509 MB across fifteen JSON files, and individual files reach 61 MB. That is slow to clone on a student connection, and single files above 50 MB draw a GitHub warning while anything above 100 MB is rejected outright — you are one collection run away from a push that fails.

The cause is threefold duplication rather than volume. Each creator record embeds its own recent_videos (or recent_posts) and a full raw provider payload; those same items are then stored again in the separate *_videos/*_posts file; and the combined *_dataset file stores both a third time. On top of that, every run is committed twice — once timestamped and once as .latest.

Fix, roughly one hour: keep one canonical *_dataset.latest.json per platform; drop the raw key from each creator (it is a provider payload you can re-fetch, not evidence you need); reference content by id from the creator instead of embedding it; and add data/raw/**/*_2026*.json to .gitignore so timestamped runs stay local. That removes well over 90% of the weight with no loss of anything the pipeline reads. Then rewrite history with git filter-repo so the old blobs actually leave the pack — deleting the files in a new commit does not shrink a clone.

Problem 2 — the collectors write files, not rows

Keep the collection logic; it is good, and the brandbridge_fields blocks show the normalisation thinking is already there. Change only where it writes. Each collector becomes backend/app/integrations/<platform>/adapter.py exposing one function that returns the normalised social contract of §5.7 — never a platform-shaped dict. Then scripts/seed_data.py, scripts/sync_social.py and the live OAuth endpoint all call the same adapter, and the ML layer never learns that YouTube counts subscribers while Bluesky counts followers.

Also move instagram_data.json out of the repository root into data/raw/instagram/, and confirm no access token was committed inside it.

PART 05

Database architecture and table structures

37 tables in nine groups. Every table here is reachable from a flow in Part 7 — nothing is speculative. The five that exist today are marked, including the one that has to change shape.

5.1 Storage principles

  • Postgres is the truth; pgvector is an index on it. No fact lives only in a vector.
  • Raw and derived both survive. campaigns.raw_brief is never overwritten by the parsed structure — the extraction experiment in Part 10 needs both.
  • Provider data is append-only and dated. A follower count is (value, captured_at, provenance), never a mutable column.
  • Scores are stored with their parts and their versions. A row in match_scores carries feature_version and model_version, so a result from week 4 stays interpretable in week 7.
  • Real and synthetic are always distinguishable. Every evidence-bearing row carries a data_provenance value; the research dataset can be filtered on it.
  • Commercial history is versioned, never edited. A counter-offer creates a new proposal_versions row.

5.4 The breaking change: dual-role identity

Do this first, in weekend 1, before anyone writes a profile endpoint

Your users table has role as a single non-null enum column, and User declares one creator_profile and one brand_profile relationship. The product requires Aarav Mehta to run Aurum Foods in brand mode and hold a creator profile — wireframe 10 shows exactly this. Changing it later means rewriting every auth dependency and every ownership check written before it.

backend/alembic/versions/0002_dual_role_identity.py
def upgrade() -> None:
    op.create_table(
        "user_roles",
        sa.Column("id", postgresql.UUID(as_uuid=True), primary_key=True),
        sa.Column("user_id", postgresql.UUID(as_uuid=True), nullable=False),
        sa.Column("role", sa.Enum("CREATOR", "BRAND", "ADMIN",
                                  name="user_role", native_enum=False), nullable=False),
        sa.Column("activated_at", sa.DateTime(timezone=True),
                  nullable=False, server_default=sa.func.now()),
        sa.ForeignKeyConstraint(["user_id"], ["users.id"], ondelete="CASCADE"),
        sa.UniqueConstraint("user_id", "role", name="uq_user_role"),
    )
    op.create_index("ix_user_roles_user_id", "user_roles", ["user_id"])

    # carry every existing account across without losing its role
    op.execute("""
        INSERT INTO user_roles (id, user_id, role, activated_at)
        SELECT gen_random_uuid(), id, role, created_at FROM users
    """)
    op.drop_column("users", "role")
    op.add_column("users", sa.Column("status", sa.String(20),
                  nullable=False, server_default="ACTIVE"))

Two rules that will save you a week

Nulls are information, not zeros. Bluesky has no view count; Instagram hides some insights; a YouTube channel can hide its subscriber count. Store NULL and let the feature builder emit a has_<field> missingness indicator. Coercing to 0 teaches the ranker that a hidden count means an unpopular creator.

Engagement rate is a fraction everywhere. Your sample file stores engagement_rate_percent: 5.86; the technical guide's match response stores 0.058. Pick the fraction, convert once at the adapter boundary, and format as a percent only in the React component.

5.12 The Wall — community tables

The Wall is where brands and creators meet each other before a campaign exists: ideas, open calls, results and questions, with follows and threaded replies. It is a genuine product surface and it is also the answer to “how does anyone arrive on this platform in the first place?” — which neither the matching engine nor the campaign flow answers.

The two rules that make the Wall safe to build

1. Wall content never enters the ranking pipeline. No post text is embedded into creator_representations, no engagement count becomes a feature, and wall_* tables are unreachable from services/discovery.py. Enforce it with an import test. If posting could move a creator up a shortlist, every score in the evaluation becomes contestable and the research contribution is gone.

2. A thread converts into an ordinary proposal. The “+ Collab” action on a post creates a normal proposals row with the thread attached as context — it does not create a parallel negotiation path. One state machine, one audit trail, one set of metrics.

Scope discipline — what the Wall is not

No direct messaging, no reposts with commentary, no notifications service, no feed-ranking model, no image processing beyond storing one file, no automated moderation. The feed is ORDER BY created_at DESC over posts from people you follow plus posts in topics you follow, and that is enough. Reports set status = HIDDEN and land in an admin list a human reads. Everything past that is future work, and saying so is a better answer than a half-built recommendation feed.

6.1 Conventions

  • Resource paths for CRUD; an explicit verb sub-path only where a state transition or an AI operation happens — /parse-brief, /confirm-requirements, /accept.
  • Every error is {"code","message","details","correlation_id"}. One DomainError hierarchy in core/errors.py, one exception handler in main.py.
  • Lists take ?limit=&offset= and return {"items":[],"total":n,"limit":l,"offset":o}. Pick offset paging and never mix it with cursors.
  • The active role travels in an X-Active-Role header, validated against user_roles on every mutating call. Never trust a role sent in a body.

api/deps.py — the three dependencies everything else uses
def get_current_user(
    token: str = Depends(oauth2_scheme),
    db: Session = Depends(get_db),
) -> User:
    payload = decode_token(token)                      # raises AuthError on bad/expired
    user = user_repo.get(db, UUID(payload["sub"]))
    if user is None or user.status != "ACTIVE":
        raise AuthError("inactive_account")
    return user

def get_active_role(
    x_active_role: Annotated[str | None, Header()] = None,
    user: User = Depends(get_current_user),
) -> UserRole:
    roles = [r.role for r in user.roles]
    if x_active_role is None:
        return roles[0]
    role = UserRole(x_active_role)
    if role not in roles:
        raise ForbiddenError("role_not_activated")     # → 403
    return role

def require_role(required: UserRole):
    def guard(role: UserRole = Depends(get_active_role)) -> UserRole:
        if role is not required:
            raise ForbiddenError(f"requires_{required.value.lower()}_mode")
        return role
    return guard

# usage:  @router.post("/campaigns", dependencies=[Depends(require_role(UserRole.BRAND))])

Why completeness_score is computed server-side

It is a weighted count of populated fields — bio 0.15, categories 0.15, languages 0.10, audience 0.15, rate card 0.20, preferences 0.15, a connected social account 0.10. It drives the UI nudge, but it is also a cold-start feature: a new creator with a complete profile should outrank a new creator with an empty one, and the ranker needs that signal as a number. If the client could send it, it would be gameable and useless as a feature.

    # R2 PLATFORM       creator must have an active rate_card_item on a required platform
    # R3 CONTENT_TYPE   creator.content_formats ⊇ at least one req.content_types
    # R4 LANGUAGE       creator.languages ∩ req.languages ≠ ∅   (skipped when req empty)
    # R5 BUDGET         min(active rate for required platform+type) ≤ req.max_rate_inr
    #                   AND creator_preferences.min_rate_inr ≤ req.max_rate_inr
    # R6 CREATOR_BLOCK  campaign.category ∉ prefs.excluded_categories
    #                   AND brand_id ∉ prefs.excluded_brand_ids

Why exclusions get their own table

Three reasons, in increasing order of importance. It powers the “show me who you filtered out” audit screen. It makes a brand trust the system, because an empty result set with reasons is debuggable and an empty result set without them looks broken. And rule accuracy and false-exclusion rate are evaluation metrics in the research plan — you cannot report them if you never stored the decisions.

def reciprocal(s_brand: float, s_creator: float, method: str = "harmonic") -> float:
    if method == "harmonic":
        if s_brand <= 0 or s_creator <= 0: return 0.0
        return 2 * s_brand * s_creator / (s_brand + s_creator)
    if method == "arithmetic": return (s_brand + s_creator) / 2
    if method == "min":        return min(s_brand, s_creator)
    if method == "weighted":   return 0.6 * s_brand + 0.4 * s_creator
    raise ValueError(method)
The example that carries the whole argument

Pair A scores Sb = 0.95, Sc = 0.20. Pair B scores 0.76 and 0.74. A conventional brand-side ranker puts A first and the creator declines, because the campaign pays below their floor and sits outside their accepted categories. Harmonic mean gives A = 0.33 and B = 0.75, so B ranks first — and B is the collaboration that actually happens. That inversion is your research contribution, it is one chart, and it belongs on the first slide of the final presentation.

Report the weights above as hypotheses under test. Compare fixed universal weights against objective-aware weights and publish the difference. Presenting hand-set business weights as learned intelligence is the criticism the plan documents warn about most often.

Stage 5 — fairness and diversity re-ranking

  1. Off by default, controlled per campaign by campaign_discovery_policy.enable_fairness_rerank. Always report the paired result — with and without — because the trade-off is the finding.
  2. MMR over the top 30: score = λ · S_r − (1−λ) · max similarity to already-selected, where similarity combines the creator vector and the follower-size band.
  3. A relevance floor is mandatory. No creator below min_transferable_fit enters the list for diversity's sake. Diversity is not fairness, and forcing an irrelevant creator in front of a brand harms the creator too.
  4. Store both reciprocal_score and reranked_score in the same row, so “relevance lost to re-ranking” is a subtraction rather than a re-run.

  8. Treat post text as untrusted everywhere it is rendered and everywhere it could reach a model. It is user-generated content that a prompt-injection fixture should target in the test suite, exactly like an uploaded PDF.
The isolation test — write it in the same PR as the first wall endpoint

A test that fails if any module under ml/ or services/discovery.py imports anything from wall. Ten lines with ast or a grep in CI. It is what lets you say in the viva, without hesitation, that posting activity cannot influence a match score — and it is the kind of claim an examiner will probe.

Tests. Post in brand mode → author renders as the brand. Double-react → one row. Comment → reply_count is 1. Follow then unfollow → feed changes. Convert a thread → exactly one proposal row with the correct initiated_by. Import-isolation test passes.

Done when two accounts can follow each other, post, reply, and turn a thread into a proposal that lands in the normal inbox — and the isolation test is green.

Three leakage rules — violating any one invalidates every number you report

Split by campaign, not by pair. The same campaign appearing in train and test leaks its requirements. Deduplicate near-identical creators before splitting — collectors produce near-duplicates and they will straddle the split. Hold out a final test set and touch it once. Tune on validation; the test set is opened in week 7 and never again.

10.4 Inter-rater agreement

Five people labelling 400 pairs will disagree, and that disagreement is a result rather than a problem. Have two raters score every pair independently, compute Cohen's κ or weighted κ per side, and adjudicate disagreements greater than one point in a recorded session. Report κ in the paper — a reciprocal ranking evaluated against labels of unknown reliability is not evidence, and showing you measured it is exactly the rigour the course asks for.

11.2 Observability

  • A correlation_id per request, generated in middleware, returned in the response and every error, and written to ai_execution_logs. One id ties a user report to a model call.
  • Every AI call logs provider, model, prompt version, latency, token estimate, status and error category. This table is your practice-metrics section.
  • Every recommendation run logs feature, model and representation versions plus candidate counts at each stage. When ranking quality changes, you will know which stage moved.
  • Social syncs log the request class, outcome and any quota error — quota exhaustion should never present as a mysterious empty profile.
  • Prometheus and Grafana are explicitly out of scope. Structured logs plus one summary notebook meet the requirement.
